### Milestone 1: Conceptual Clarity on dot() vs inner() vs matmul()
- **Changes Made**:
  - Established clear distinctions between three matrix operations
  - Documented NumPy semantics for each operation
  - Identified rationale for implementing matmul() instead of dot()
- **Key Learnings**:
  - **dot()**: In NumPy, dot() has complex, context-dependent behavior
    - 1-D @ 1-D → scalar (sum of products)
    - 2-D @ 2-D → matrix multiplication
    - N-D @ N-D → complex behavior with axis=-1 and axis=-2
    - Difficult to implement consistently across dimensions
  - **inner()**: Cleaner semantics, mathematically well-defined
    - Performs cartesian product over non-last dimensions
    - Contracts over last dimension
    - Output shape: src1.shape[:-1] + src2.shape[:-1]
    - Example: [2,3] x [2,3] → [2,2] (not [2,2] for matmul)
  - **matmul()**: Modern, explicit matrix multiplication semantics
    - 1-D @ 1-D → scalar (dot product)
    - 2-D @ 2-D → standard matrix multiplication
    - N-D @ N-D → batch matrix multiplication with broadcasting
    - Batch dimensions are broadcast together (not cartesian product)
    - Output shape for N-D: broadcast(src1.shape[:-2], src2.shape[:-2]) + [m, p]

- **Why matmul() over dot()**:
  - More explicit and consistent semantics
  - Aligns with modern linear algebra libraries (PyTorch, TensorFlow)
  - Clearer use case: matrix multiplication operations
  - Easier for embedded systems (no context-dependent behavior)
  - dot() is fundamentally ambiguous for N-D tensors

  /* Key stride computation for broadcasting */
  for (int i = 0; i < max_batch_ndim; i++) {
      int a_idx = a_batch_ndim - max_batch_ndim + i;
      if (a_idx >= 0 && a->dims[a_idx] > 1) {
          /* Compute stride for this dimension */
          int stride = 1;
          for (int j = a_idx + 1; j < a->ndim; j++) {
              stride *= a->dims[j];
          }
          a_batch_strides[i] = stride;
      } else {
          a_batch_strides[i] = 0;  /* broadcast (dimension is 1 or doesn't exist) */
      }
  }

## Technical Context

### Architecture Decisions
1. **Separate matmul() and inner() functions** instead of unified dot()
   - Rationale: Different semantics for batch dimensions (broadcast vs cartesian)
   - Cleaner API for users
   - Easier to maintain and reason about behavior

2. **Temporary reshape for 1-D tensors** in matmul()
   - Rationale: Simplifies core logic to always work with ≥2-D tensors
   - Minimal overhead for temporary allocations
   - Cleaner code flow with explicit squeeze semantics

3. **Broadcasting stride computation**
   - Rationale: Efficient handling of broadcast dimensions
   - Stride = 0 indicates broadcast (no data movement for that dimension)
   - Consistent with NumPy broadcasting model

2. **Batch Dimension Abstraction**: Separate batch dims from matrix dims

## Important Notes

### Key Implementation Insights
1. **Dimension Squeezing**: When 1-D tensors are expanded to 2-D, the squeezing at the end is critical:
   - 1-D @ 1-D becomes [1,n] @ [n,1] = [1,1], squeeze both → [1]
   - 1-D @ 2-D becomes [1,n] @ [n,m] = [1,m], squeeze left → [m]
   - 2-D @ 1-D becomes [m,n] @ [n,1] = [m,1], squeeze right → [m]

2. **Broadcasting Strides**: A stride of 0 means that dimension should be repeated:
   - When src1.shape[i] = 1 and src2.shape[i] = k, stride[i] = 0 for src1
   - The multiplication in the main loop (batch_coord * stride) gives 0 offset
   - Effectively reusing the same "plane" across all batch indices

3. **Output Indexing**: Complex index calculation for different squeeze patterns:
   - No squeeze: dst_idx = batch_idx * m * p + i * p + j
   - Left squeeze: dst_idx = batch_idx * p + j
   - Right squeeze: dst_idx = batch_idx * m + i
   - Both squeeze: dst_idx = batch_idx
